# Seguridad orientada a amenazas

Delimita activos, actores, datos sensibles, fronteras de confianza, entradas/salidas y superficie realmente modificada. Modela abusos plausibles para ese flujo (suplantación, autorización por objeto/tenant, entrada maliciosa, exposición, repetición, dependencia); sigue datos hasta el uso sensible. Verifica controles efectivos, no solo validación sintáctica o instrucciones de prompt.

Para cada recorrido sensible, dibuja **dato → transformación → uso/efecto sensible → control → posible bypass**. Propón al menos una condición que refutaría tu hipótesis de seguridad y comprueba implementación/configuración/test pertinente. “Hay middleware/auth” no demuestra autorización del objeto: un caso negativo útil es identidad autenticada A solicitando recurso perteneciente a B; verifica que se deniega sin filtrar contenido ni permitir efectos. No copies valores secretos a la entrega; reporta nombre de variable/ruta y ubicación redactada, nunca el valor.

Contrasta secretos, logs, errores, permisos, rutas, datos no confiables y fallos de terceros donde apliquen. Usa documentación/avisos oficiales versionados cuando afirmes una vulnerabilidad o comportamiento externo. Para cada riesgo aporta precondición, ruta/evidencia, impacto y mitigación verificable; separa confirmado, probable y no verificable. No inventes severidad/CVE ni declares cumplimiento.

En operaciones de archivos destructivas/reemplazos, verifica una raíz permitida explícita y que el objetivo sea descendiente estricto (no la raíz misma). Canonicaliza/normaliza y comprueba symlinks en componentes y objetivo; no confíes solo en prefijos de strings (`/safe2` no es hijo de `/safe`). Comprueba ownership desde estado confiable/canónico, no desde un path declarado por quien solicita la operación. Considera TOCTOU entre comprobar y abrir/renombrar: usa primitive segura/descriptor si existe; si la carrera no se puede cerrar, reconoce el límite y reduce alcance. Si el destino no pasa validación, rechaza; no caigas a una ruta amplia/default para “recuperar”. Prueba traversal, symlink, raíz como target, reemplazo de componente/race y ruta externa en fixture aislado, sin tocar datos reales.

Supply chain: cuando el cambio altera dependencia, lockfile, script de build/instalación o artefacto descargado, revisa procedencia/versiones, scripts ejecutados, integridad y alcance de permisos con fuentes/registros ya disponibles. No instales herramientas ni dependencias para auditar; ausencia de evidencia no es certificación.

Mantén revisión estática separada de pruebas dinámicas; exploits, escaneo intrusivo, datos reales y sistemas fuera del scope requieren autorización explícita. No instales scanners/MCP ni reveles secretos para completar una lista genérica.
