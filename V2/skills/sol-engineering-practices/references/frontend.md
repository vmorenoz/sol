# Frontend, accesibilidad y navegador

Aplica solo a interfaz afectada. **Al implementar**, primero identifica componentes, sistema visual, convenciones de estado (local/remoto, carga/error/vacío), tokens y patrones existentes; reutilízalos si encajan, y justifica una nueva abstracción/variante por necesidad del producto. Sigue el recorrido real y estados que cambian el resultado, no agregues componentes por checklist.

Para diálogos/modales, cuando existan: abre con teclado; observa foco inicial dentro del diálogo, orden/tab trap según patrón, Escape/cancelación si corresponde, cierre y restauración del foco al disparador (o destino lógico si desapareció). Para formularios, induce un error con dato sintético y verifica asociación campo↔mensaje (`aria-describedby`/equivalente), foco útil y anuncio accesible según implementación; DOM estático por sí solo no demuestra anuncio de screen reader.

Identifica estados asíncronos pertinentes (pendiente, éxito, error, reintento, doble submit/cancelación) y comprueba que feedback y controles coinciden con el resultado. Elige viewport representativo según breakpoint/contenido y repite con zoom o reflow cuando el criterio lo requiera; registra tamaño/zoom, ruta y estado. Comprueba semántica/nombres, teclado/foco, legibilidad, contraste y movimiento reducido donde aplique. Distingue inspección DOM, checker, captura, interacción real y tecnología asistiva: no declares que probaste lector de pantalla si solo inspeccionaste markup.

Si un navegador o herramienta ya está disponible y autorizada, úsalo para reproducir interacción, errores de consola/red o apariencia del estado pertinente. No presupongas Chrome DevTools MCP ni instales nada. Si no hay entorno, inspección estática puede orientar pero visual/interactivo queda no ejecutado. Usa datos sintéticos y registra viewport/estado para capturas autorizadas. No impongas una estética genérica ni afirmes accesibilidad/rendimiento solo por markup o screenshot.
